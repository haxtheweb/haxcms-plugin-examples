# Conformance fixtures

Tiny plugins used by the executable spec conformance cases (`conformance/cases/*.yaml`, `run` blocks). They exist to exercise the platform, not to be useful: `fx-probe-*` log every hook call and take a behavior per hook from settings (veto, throw, hang, invalid return, set a field); the rest each prove one rule (routes and credentials, requirements, page cache, singleton, SSR, plugin-defined hooks, suggests, user records, config scope, transactions, theme change, and from `cases/platform.yaml`: schedules `fx-scheduled`, legacy settings and required fields `fx-legacy-setting`, declarative proxies `fx-proxy`, `ctx.exec` `fx-exec`, optional auth and the response envelope `fx-optional`, no re-entry `fx-reentry`, plugin metadata on core records `fx-meta`, render stages `fx-stage-seal` / `fx-stage-transform`, listed pages `fx-listed`, the system engine `fx-system`; atomic transactions from `cases/hooks.yaml`: `fx-atomic`). Fixtures named in validator cases (`fx-contrib-required`, `fx-spawn`, `fx-detached-wait`, `fx-tracker`, `fx-no-security`, `fx-pack-code`, `fx-bad-manifest`, `fx-future`, `fx-no-handler`) are deliberately invalid.

Every fixture with code ships both runtimes (`src/nodejs/index.js` and `src/php/Plugin.php`, the PHP one mirroring the Node one), so the same cases run against both: `node conformance/run.mjs --runtime php` runs the PHP entries through the reference engine's bridge, and a backend's adapter runs whichever runtime it is (haxcms-php's runs the PHP entries natively). Fixtures that are deliberately broken, or that only prove a Node-specific rule (`fx-spawn`), stay Node only. `fx-only-nodejs` and `fx-only-php` ship one runtime on purpose: the other backend refuses them (load-118, load-119; a case with `runtimes: [...]` runs only on those backends).

Run: `node conformance/run.mjs` (also part of `npm test`).
