# Import from VitePress (core)

**Today:** `POST /system/api/v1/site/import/vitepress` in [haxcms-nodejs](https://github.com/haxtheweb/haxcms-nodejs) (`src/systemRoutes/v1/routes/imports/convertVitepressToSite.js`, mirrored in [haxcms-php](https://github.com/haxtheweb/haxcms-php)) takes a GitHub repository URL, reads the file tree and `.vitepress/config.*` through GitHub's API, renders every page with markdown-it (OER containers, footnotes) and returns items, files and the site license for `createSite`.

**As a plugin:** implements the core contract `import.platform` (dispatch `chosen`). Markdown is converted through the platform (`ctx.contracts.call("import.file", ...)`, answered by the `import-markdown` plugin), so this plugin carries no markdown parser.

- **Source:** a GitHub repository URL (`https://github.com/<owner>/<repo>`, optionally `/tree/<branch>`), read from `api.github.com` (repository and file tree) and `raw.githubusercontent.com` (files), the only hosts it may reach; or an uploaded zip of the repository (`files: [{ name: x.zip, data }]`, read with `ctx.archive.read`; a GitHub download's top folder is dropped), which fetches nothing.
- **Config, never executed:** the config is found as core finds it (`docs/.vitepress/` first, then `.vitepress/` at the root, then the shallowest). `title`, `base`, `siteUrl` and the `sidebar` literal are read as plain data (strings, arrays, objects, numbers, booleans, null; comments skipped, matches inside strings and comments ignored). A sidebar that is a function call or variable falls back to the markdown file tree, as VitePress itself does. A sidebar map (path prefix to array) is merged in order.
- **Outline:** sidebar entries with `text` become pages (with `link`) or landing pages (only `items`), nested by `items`; links are resolved after removing `base`, to `x.md` or `x/index.md`. Without a sidebar, every `.md` under the docs root (not `.vitepress/` or `node_modules/`), shallowest first, index first.
- **Pages:** the front matter `title` replaces the sidebar label. `VideoEmbed` becomes `video-player` (caption kept); other Vue components are unwrapped to their content. Containers: the OER containers (`learning-objective`, `assessment`, `practice`, `learning-component`, `instructional-pattern`) become `oer-schema` with their attributes as properties, as in core; `info`, `tip`, `warning`, `danger` become `stop-note`, `details` becomes `<details>`, any other container is unwrapped. Code fences keep their language (line highlights dropped).
- **Links and files:** in-site links point at the imported slugs; images become `media-image`; repository images and documents (absolute references look in `public/` first) are listed in `files` with their raw URLs for core to fetch; other relative references point at the raw file. A page that cannot be read links to the published page when `siteUrl` is set. Scripts and inline handlers are dropped (core sanitizes again).
- **Input:** `{ url }` or `{ files: [{ name, data (base64) }] }`. **Output:** `{ title, items: [{ id, title, slug, parent, order, indent, content, metadata: { sourceType, vitepress: { repo, branch, path }, source? } }], files }`, or `{ error }`.

**Not ported yet**

- License and attribution: core reads `license`, `defaultAuthor` and `workTitle` (config and front matter), sets the site license and appends a `license-element` to each page. `import.platform` has no place for site settings yet.
- Footnotes, tables and other markdown the shared converter does not know; `truncated` / `unmappedComponents` reporting; the fetch time budget (the 500-page cap is kept).
- From a zip upload, images and files are not listed (`files` takes URLs only), so their references stay as written.

**Differences from core:** the default VitePress containers are mapped (core leaves their `:::` lines as text); repeated slugs get `-2`, `-3`; a sidebar link already written with `base` does not get it twice in `metadata.source`.
