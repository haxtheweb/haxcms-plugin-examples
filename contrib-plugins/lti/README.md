# LTI 1.3 tool (community draft, Node first)

Lets an LMS open a HAXcms site or lesson for its teachers and students, signed in by the LMS. A running HAXcms becomes an LTI 1.3 tool: Canvas, Moodle, D2L Brightspace, Sakai, Schoology or Blackboard starts a login, posts a signed launch, and the person lands on the address the launch names. Off until you enable it, and it needs the **Tool URL** setting (this HAXcms's public address) before it does anything.

This is the launch half of https://github.com/haxtheweb/issues/issues/3345. Deep linking and grade passback are https://github.com/haxtheweb/issues/issues/3346.

## Setting it up

1. Enable the plugin and set **Tool URL**.
2. Read `ltiToolConfiguration` and paste its three addresses into the LMS's tool registration: the login address (OIDC initiation), the redirect address (launch) and the key set address (JWKS).
3. Save what the LMS gives back with `ltiPlatformSave`: its issuer, the client id it assigned, the deployment ids, its authorization address and its key set address. All addresses must be https.

## What a launch does

1. **Login.** The LMS calls `ltiLogin` (or `ltiLoginGet`). The plugin finds the registration for that issuer, remembers a state and a nonce for five minutes, and sends the browser to the LMS.
2. **Launch.** The LMS posts a signed token to `ltiLaunch`. The plugin uses the state once, checks the RS256 signature against the LMS's public keys, then every claim: issuer, audience, expiry, nonce, deployment, message type, version, and that the address is the one the login named and belongs to this HAXcms.
3. **Arrive.** The browser is sent to the launched address with a single-use ticket in the URL fragment. `ltiLaunchClaim` exchanges it, once and within 60 seconds, for who arrived and whether they may edit.

## Who can edit

People the LMS calls Instructor, Content Developer or course Administrator arrive as `editor`, so teachers author in place. Everyone else arrives as `viewer`: read-only, with the session knowing who the student is. Turn **Teachers can edit** off to make every launch read-only. A launch that does not say who the person is can read and never edit.

## What it does not do yet

- **It does not sign anyone in.** Core has no API a plugin can call to start a session, so the launch ends in a ticket for core (or the front end) to claim. `spec/GAPS.md` item 1w proposes the API and lists the other holes this draft found.
- **Node only.** The PHP entry follows once the shape is agreed; until then it does not load on a PHP backend.
- **No deep linking, no grades, no dynamic registration.**

## What it implements

| Kind | Name | Runs when | What this plugin does |
|---|---|---|---|
| operation | `ltiLoginGet` | `GET /system/api/v1/plugins/<id>/login` (public) | The same login when the LMS sends it as a GET. |
| operation | `ltiLogin` | `POST /system/api/v1/plugins/<id>/login` (public) | Starts the OIDC login an LMS sends as a form POST: finds the registration for its issuer, remembers a single-use state and nonce, and sends the browser to the LMS's authorization endpoint. |
| operation | `ltiLaunch` | `POST /system/api/v1/plugins/<id>/launch` (public) | Verifies the signed launch the LMS posts (state used once, RS256 signature against the LMS's key set, then every claim), and sends the browser to the launched address with a single-use ticket that says who arrived and whether they may edit. |
| operation | `ltiLaunchClaim` | `POST /system/api/v1/plugins/<id>/launches/claim` (public) | Exchanges a launch ticket, once and within 60 seconds, for who the LMS said the person is and whether they may edit; stands in for a core sign-in API. |
| operation | `ltiJwks` | `GET /system/api/v1/plugins/<id>/jwks` (public) | Publishes this tool's public keys for LMSs to register; the key pair is made on first use and the private half never leaves the server. |
| operation | `ltiToolConfiguration` | `GET /system/api/v1/plugins/<id>/configuration` (bearerAuth + userTokenHeader) | Lists the addresses an admin pastes into the LMS when registering this tool. |
| operation | `ltiPlatformList` | `GET /system/api/v1/plugins/<id>/platforms` (bearerAuth + userTokenHeader) | Lists the LMSs registered with this tool. |
| operation | `ltiPlatformSave` | `POST /system/api/v1/plugins/<id>/platforms` (bearerAuth + userTokenHeader) | Adds or changes an LMS registration (https endpoints only, one registration per issuer and client id) and keeps the list of hosts the plugin may fetch keys from in step. |
| operation | `ltiPlatformDelete` | `DELETE /system/api/v1/plugins/<id>/platforms/{id}` (bearerAuth + userTokenHeader) | Removes an LMS registration, its cached keys, its logins in progress and its unclaimed launches; launches from it stop working at once. |
