# Routes and security

Part of the HAXcms plugin specification (decision source: https://github.com/haxtheweb/issues/issues/3176).

## Routes and security

- **Unified OpenAPI contract.** Each plugin's `config/openapi.yaml` is validated, and the platform builds one contract from the enabled plugins. Every path is forced under `/v1/plugins/<id>/` (`/system/api/v1/plugins/...` and `/x/api/v1/plugins/...`; plural in both). Plugins cannot place routes elsewhere or change a core path, a disabled plugin's paths 404, and plugins can build on each other (`authproviders/list` from one plugin, `githubauth/revokeAll` from a dependent). Each plugin's own spec is also served at `/v1/plugins/<id>/openapi.json` and `.yaml`. Which API an operation mounts under is set by `x-hax-scope`: `site` (default; `/x/api/v1/plugins/<id>/`, the site is the request's site) or `system` (`/system/api/v1/plugins/<id>/`), at the document root as a default and overridable per operation. Announcements is system scope.
- **Security is explicit and fail-closed.** Every operation declares `security`; policy is derived from the unified contract. Levels: authenticated with user token (system), authenticated for a site, `optional` (spelled as an empty requirement next to a real one, `security: [{}, { bearerAuth: [] }]`; anonymous calls reach the handler with `ctx.user = null` and the handler applies a setting-based filter, as comments does for visitors and views will for anonymous reads; `[{}]` alone is rejected, use `x-hax-public: true` for that), and `x-hax-public: true`. `x-hax-public: true` is per operation, flagged by audit, rate limited by the system's built-in limiter, and a per-operation `x-hax-rate-limit` may tighten it. Operations opt in to MCP with `x-hax-mcp: true`: when the optional core MCP plugin is enabled, those operations are offered as MCP tools and the caller's own permissions still apply; nothing is exposed by default. Operation ids and schema names are prefixed with the plugin id; `assets/` and `openapi.*` are reserved sub-paths.
- **Declarative proxies.** An appstore provider or similar plugin that only adds a secret and forwards a search needs no code: a GET operation may carry `x-hax-proxy: { url, query, pass }`. Core calls `url` with the fixed `query` (templates may read `{{settings.<field>}}` and nothing else) plus only the caller's query parameters named in `pass`, and returns the status and body. The host must be in `egress`; the response never includes the settings used. A plugin whose operations are all proxies has no `entry` or `runtimes` and runs the same on every backend (youtube, vimeo, giphy, unsplash, flickr). Pagination that hands the browser a full upstream URL (Vimeo's and Unsplash's `paging.next`) would bypass the proxy and leak or lose the key, so those providers use page-number pagination through the proxy instead.
- **Version confidentiality** (https://github.com/haxtheweb/issues/issues/3174) applies unchanged: no route exposes the HAXcms version without both credentials, and unauthenticated entity listings contain only site-scope descriptors.
- **List conventions** follow the existing API: `page.limit`, `page.offset`, `sort`, `filter[...]`, `fields`.

## MCP

MCP support is an optional core plugin (`mcp`): installed at system level, enabled per site, never required, and blockable by deployment config (HAXiam blocks it for now). It builds on https://github.com/haxtheweb/haxcms-mcp, today a separate Python MCP server that is an HTTP client of a running HAXcms (117 tools, resources and prompts, pinned to 26.8.1), and on the existing core `mcp.enabled` / `mcp.readOnly` config, which moves into this plugin's CMI settings through its install hook.

- **Separation.** haxcms-mcp stays a stand-alone server. The plugin provides discovery, tokens and policy; it does not serve MCP itself.
- **Core tools.** The existing hand-written core tools stay in haxcms-mcp for now; marking core's own operations `x-hax-mcp: true` so core and plugin tools come from one place is a later migration.
- **Tools.** Only plugin operations with `x-hax-mcp: true` are offered. The plugin serves a discovery operation listing, per site, the opted-in operations (with their OpenAPI schemas) and the prompts from `register.before.prompts`, so the MCP server can add plugin tools without a release.
- **Tokens.** Clients use scoped tokens issued by the plugin, not a user's dashboard login: each token is bound to one site (or the system), to read-only or read-write, optionally to a list of plugins, has an expiry, and is revocable from the plugin's screen. The caller's permissions are the intersection of the token's scope and the issuing user's.
- **Logging.** Every MCP call is written to the unified log with the token id.
