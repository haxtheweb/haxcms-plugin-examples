# Spec gap list (for review)

Found while writing the examples, validator and conformance cases. Each is a decision or a hole, not a bug report. Resolved items are kept so the reasoning is visible.

## Resolved in this PR
1q. **Found by building the last twelve community plugins** (csp-headers, minify-html, webhooks, glossary, onboarding-tour, api-docs, media-library, seo-meta, xapi-statements, site-stats, dark-mode-toggle, link-checker). What they needed:
   - *Ordering between strangers.* csp-headers must hash the document after minify-html changes it and before page-cache stores it, and none of them know each other, so priority numbers would be guesswork. Hook contracts may now define `stages` (render.after: `transform`, `seal`, `store`); subscriptions pick one and stages run in order before priority. page-cache moved to `store`.
   - *Admin-chosen destinations.* webhooks and xapi-statements send data to URLs admins enter, which `egress` could not list. An `egress` (and `privacy.recipients`) entry may name a setting; only those URLs' hosts are reachable, and the derived tag `admin-chosen-hosts` shows it. link-checker must reach any host: `{ any: true, reason }`, derived tag `reaches-any-host`. The harness's SSRF guard (private, loopback and link-local addresses refused) applies to every fetch.
   - *Declarative UI beyond modals.* onboarding-tour is a dashboard tour over anchors app-hax promises to keep (`action.kind: tour`, a fixed anchor list), with no code at all. Locale overlays translate declarative UI by key (`dashboard.<id>.<path>`), and the validator rejects keys that name nothing.
   - *The unified contract was not readable.* api-docs needed `ctx.plugins.contract()`; core strips `x-hax-proxy` from it so upstream URLs and key templates never leave the server.
   - *Extension side effects.* A mediaItem (extends file) save also fires `file.after.save`, so media-library's own hook saw its own records. `ctx.entityType` now carries the concrete type (spec/04 already promised it).
   - *Plugin fields on core records.* publish-scheduler, reading-time and seo-meta keep values on pages. They live under `metadata.plugins.<id>` in the record, declared in `entities.yaml` `metadata.<type>.fields` (with an optional `form` for the page settings dialog). Core drops undeclared or mistyped fields with a warning, as decided for undeclared additions, and leaves data of uninstalled plugins alone.
   - *Theme facts.* dark-mode-toggle must know whether a theme supports dark. Theme registry entries gained `colorSchemes`, and `ctx.registries.theme(element)` reads the merged registry.
   - *Loops.* changelog saving a page from `git.after.commit` looped forever (git commits, fires the hook, changelog saves, and so on). A subscriber that is already running a hook is not re-entered for the nested event (spec/06); the nested change is picked up by the next run.
   - *Schedules could not be tested.* Added a `schedule` step; core runs each job as one bulk transaction (publish-scheduler's batch is one git commit), fires `schedule.before.run` (maintenance-mode skips jobs) and `schedule.after.run` (notifications reports failures).
   - *Community plugins depending on community plugins.* spam-guard subscribes to comments' own `comments.before.create` as a hard dependency; notifications subscribes softly (suggests). comments gained `hookDefinitions`.
   - *Personal data that left the server.* xapi-statements sends statements to an LRS; the `privacy.export` / `privacy.delete` contracts account for those copies, now that core calls them during export and erase.
   - *Still open:* `needs-server` is shown for a CLI-only plugin (site-stats), which needs a backend but not a web server; `staticFallback` plugins still get `needs-server`. Worth a wording change in the derived tags.
1p. **Found by building spam-guard, notifications, changelog, publish-scheduler, reading-time and maintenance-mode.** Covered in 1q (loops, schedules, plugin fields, cross-plugin hooks); also: `asUser: null` and a `clock` step for tests, and `plugin.after.enable` / `plugin.after.disable` reach every subscriber (page-cache clears on any plugin change).
1o. **Found by building vimeo, giphy, unsplash, flickr, open-media-apps, feeds, sitemap, search, page-cache and importer-wordpress** (`core-plugins/`). What they needed:
   - *Duplicate provider code.* Four keyed appstore providers (and youtube) were the same fifteen lines: add a secret, call one host, pass the answer back. Added `x-hax-proxy` on GET operations (`url`, fixed `query` with `{{settings.<field>}}` templates, `pass` list); a plugin whose operations are all proxies has no entry or runtimes and works on both backends. youtube lost its code. Link-style pagination would hand the browser an upstream URL without the key, so those providers page by number.
   - *Install code for moving settings.* Six plugins carried near-identical `plugin.after.install` hooks to move a value from `site.json` or the core config. Core now does it from `legacy.settings` on first enable (typed to the form field, empty parents pruned, through the normal hooks); the hooks and the `site:*`/`settings:*` capabilities they needed are gone.
   - *Requirement code for required fields.* `plugin.before.requirements` hooks mostly checked one required setting. A required settings field without a value is now an unmet requirement by itself; four hooks were removed.
   - *Keyless providers today are always on.* open-media-apps is a pack, so it is off until enabled, which would take five apps away from every existing site. **Needs a decision** (item 20).
   - *Core names plugin files.* `llms.txt` links `rss.xml`, `sitemap.xml` and `lunrSearchIndex.json`. `managedFiles` entries may now carry a `title` (and `type`); core lists advertised files of active plugins under Resources and names none itself.
   - *Public URL and clock.* Feeds and sitemaps need the site's public base URL (`ctx.site.url`, with core's fallback when no domain is set) and a clock that tests can freeze (`ctx.now()`, `run.now`, a `clock` step). The validator warns on `Date.now()`, `time()` and `microtime()`; mcp and announcements moved to `ctx.now()`.
   - *What is public.* Core's llms.txt skips unpublished, hidden and region pages, but its feeds, sitemap and search index include them (found in haxcms-nodejs `HAXCMS.updateAlternateFormats`: the text of unpublished pages is in the public `lunrSearchIndex.json`, and the index's symbol cleanup is a string where a regular expression was meant, so it never runs). Added `entities.list("page", { listed: true })` as the one rule for anything published.
   - *Caching needs to know what is personal.* The render context gained `cacheable` (a plugin whose output differs per visitor sets it false); page-cache stores only dynamic, anonymous, cacheable renders and clears on page, site, any plugin's settings, and plugin enable/disable.
   - *Two importers.* `import.platform` was called on every implementer. Core contracts now say `dispatch: all` or `chosen`; import is `chosen` (the screen lists implementers by title) and calling it without a choice is refused. The contract output gained `files` so an importer can hand media to core instead of downloading it.
   - *Categories.* Added `publishing` (feeds, deploys).
1n. **Found by building comments, plausible-analytics, rsync-deploy, a11y-check and music-blocks** (`contrib-plugins/`, the first community-style plugins; three are Node only). What they needed:
   - *Setting-dependent consent.* Plausible sets no cookies and asks for consent only when a site wants it, but `requiresConsent` was static. Added `privacy.consentSetting` (a boolean setting); core resolves the effective list before cookie-consent reads it, so the two plugins still never name each other.
   - *Veto status was dropped.* `ctx.veto(msg, 422)` came back as 409 from config saves, enable and disable. The harness now passes the status through everywhere.
   - *`optional` auth had no spelling.* spec/05 named the level but nothing implemented it. It is `security: [{}, { bearerAuth: [] }]`; anonymous calls get `ctx.user = null`. A public or optional call without credentials no longer sees the harness's default user. `[{}]` alone is rejected by the validator.
   - *Response envelope collided with records.* A comment `{ id, status: "pending", body }` was read as `{ status, body }`. A value is a response only with an integer `status` and no keys besides `status`, `headers`, `body` (spec/13).
   - *Personal data in published copies.* Erasing a user removed their comments from the store but not from statically published pages, and the after hook could not know which pages (the rows were gone). Added `user.before/after.export` and `user.before/after.erase` (82 hooks now); erase runs as one transaction so marks carry from before to after. Export and erase now also call the `privacy.export` / `privacy.delete` contracts, which were defined but never called.
   - *Partially static plugins.* `staticCapable` is a yes/no, but comments works statically in a reduced form. Added `staticFallback` (one sentence shown to owners).
   - *Processes could not be tested or checked.* rsync-deploy had to either run rsync in tests or carry a test-mode flag. Added `ctx.exec(cmd, args, { files })`: list-enforced at run time, no shell, private temp files for credentials (`{tmp}`), faked in cases with `run.exec` and asserted with `expect.exec`. The validator now also checks literal command names against the `exec` list.
   - *Save warnings went nowhere.* `ctx.warn` from `page.before.save` and `config.before.save` was collected and then dropped. Saves now return warnings to the caller.
   - *Render had no mode.* a11y-check must outline problems in the editor's preview but never in published pages. The render context now has `mode`: `dynamic`, `preview` or `publish`.
   - *Pack topology.* The harness's rebuild now returns the block list (active plugins only) and the element registry (every installed element), and disabling a pack whose blocks are on pages succeeds with an `inUse` list, as spec/07 described. Test steps gained `delete`.
   - *Runtime warning.* The single-runtime warning fired for every plugin. Core plugins must have both runtimes (an error); community plugins get a notice naming the backend they will not load on.
1m. **Found by building outline, files, log, mcp, importer-html and the packs** (`core-plugins/`, `contrib-plugins/`). Plugins needed: `ctx.entities.delete`, `ctx.files.put/remove` for a site's `files/` folder, `$ctx->runTransaction` in PHP, the site token header in the harness, checked `legacy.routes`, and a rule that a missing optional value is written as `null` in both runtimes. A dependency must be loaded for its dependents (outline stays disabled without git). Core contracts (`schema/core-contracts.yaml`: `import.platform`, `log.sink`, `privacy.export`, `privacy.delete`) replace hard-coded importer and log calls; the harness calls them and flushes log entries to sinks (never a sink's own entries). MCP needed `ctx.plugins.operations({ mcp: true })` and `ctx.plugins.prompts()`, and `rest.before.request` / `rest.after.request` around every operation for its read-only guard. Test steps gained `headers` and `capture` (`{{$name}}`). Packs pointing at published packages use package specifiers; front-end-only packs are exempt from executable cases but warned without element tests.
1l. **Found by building author-profile, pwa, youtube, git and agent-skills.** Plugins needed to: write generated files (`ctx.files.writeManaged`, limited to `managedFiles` patterns, one owner per path); list their own package data (`ctx.package.list`); read the site skills of other plugins (`ctx.plugins.skills`); reach the core configuration to move secrets out of it (entity type `config`, `settings:read/write` capabilities, `legacy.settings` values with `config:`); fire the core hooks they own (`git` fires `git.*`). Generated JSON must be byte-identical across backends (PHP pretty-prints with four spaces; caught by the agent-skills parity run), so spec/13 now fixes the format. The validator's process scan flagged `regex.exec()` as spawning a process; it now looks for `child_process` in JS and the process functions in PHP. Test cases may test hooks a plugin fires, not only ones it subscribes to. Parity checks can ignore legitimately different values (`parityIgnore`, for commit hashes). Themes that read author fields will read the plugin's published profile, which means themes `suggest` the plugins whose data they show. Core bug noticed: the boilerplate agent-skills `index.json` keeps literal quotes around some descriptions.
1k. **Found by building cookie-consent, google-analytics and regions** (`core-plugins/`). Plugins needed to: write their own settings (`ctx.config.save`, for install migrations); see which active plugins track (`ctx.plugins.list`); reference their own front-end files in output (`ctx.assets.url`); say whether settings are per site (`settingsScope`); declare the old locations they replace (`legacy.tags`, `legacy.routes`, `legacy.settings` now have a shape); tell core which pages are fragments (`rebuild.before` now returns `fragments`, replacing core's region-specific llms.txt logic). haxProperties settings fields have no default key, so defaults live in `config/settings.defaults.json`. A plugin's own config hooks must run while it is inactive (otherwise the setting that activates it cannot be validated). A hook that read `site`, triggered another change to it, then saved its stale copy silently lost that change: `ctx.entities.save` now refuses stale copies (`conflict: true`). `privacy.requiresConsent` is the list of categories to ask about.
1j. **Executable conformance.** 49 of 92 spec cases now run against the reference harness over fixture plugins (`conformance/fixtures/`); the rest need surfaces the harness does not model yet (assets, CLI, install, export, MCP, scheduler, front end). Found along the way: hook names could not start with a dashed plugin id (`fx-definer.after.ping`), so the hook name pattern now allows it; operations without `security` or `x-hax-public` are now rejected by the validator (fail-closed was stated but not checked); operation id prefixes are compared in camel case (`fx-routes` → `fxRoutes`).
1i. **Backend platform contract written** (spec/13: layout, loader lifecycle, entry points, `ctx` including `hooks.fire`, operations, hook dispatch, settings and secrets paths, served surfaces, adapters). **Reference harness** (`harness/`): executable `run` blocks in plugin test cases, run in Node and PHP with parity; announcements 30/30 and example 25/25 checks pass. The example now implements its operations in both runtimes and declares `network:egress` for the appstore broker.
1h. **CLI aliases.** Plugin commands may declare a top-level `alias` (`hax whats-new`); core command names are reserved; colliding aliases between plugins are dropped with a warning.
1g. **Separation made explicit.** Core never names a plugin: front-end extension points (dashboard slots and contributions, Merlin, blocks, appstore, contract-registered operations, generic events) and CLI commands contributed through `registries/cli/` as `hax <plugin id> <command>`. One contributions endpoint for the dashboard. Conformance cases: a disabled plugin leaves no trace; core source contains no plugin references. A small DDD chip element is the plan for badges; `accent-card` for modal cards for now.
1f. **Plugins reuse platform UI.** Dashboard contributions (`registries/dashboard/`) are declared as data and rendered by app-hax with existing elements; announcements ships no front-end code. Merlin opens them with `hax-dashboard-open`. Rendering contributions is future app-hax work.
1e. **Found while building announcements.** Routes needed a way to pick the system or site API: `x-hax-scope` (document default, per-operation override). Shipped read-only content needed a store: `package` scope under `data/`, read with `ctx.storage.read`, other data files with `ctx.package.read`. Dashboard elements needed a role: `admin`. Operation ids must start with the plugin id (now validated).
1d. **No `defaultEnabled`.** Required core plugins are on; everything else is off until enabled; `--all-sites` is a CLI convenience. Skeletons are starting points with no later effect.
1c. **Transactions join, packs are authoring-only.** Nested transactions join the outer one; any plugin can open or add to a bulk transaction. The abstraction is named the HAX backend platform contract. Packs shape the authoring appstore and block list at rebuild time; `wc-registry.json` and CDN hydration are unchanged. Disabling a pack in use is allowed with a notice listing affected pages.
1b. **Soft hook subscriptions, no core filters, transactions, packs.** Subscribers choose dependencies or suggests for another plugin's hooks; core offers no criteria filters. Transactions with mark-and-defer (`transaction.*` hooks). Required core plugins declare dependencies (`outline` → `git`). Core plugins mirrored into each backend's core plugins folder; Node first, then PHP. Element packs enabled per site, chosen by skeletons; `siteTypes` reserved for recommendations.
1a. **Aliases, plugin-defined hooks, required core plugins.** Hook definitions share `hook-contracts.schema.json`; `aliasOf` with `entities` and `changed` filters; new aliases `page.*.delete`, `file.*.save` / `.delete`, `theme.*.change`. Plugins define namespaced hooks via `hookDefinitions`. `outline`, `git` and `files` proposed as required core plugins (structure, not optionality). Health chips live on the plugin dashboard and work without the optional log plugin.
0z. **Full hook contracts (was item 6).** Every operation has a before and an after hook. `schema/hook-contracts.json` lists each hook's trigger, subject, previous, return, veto and detach rules; spec/06's table is generated from it and checked by `npm test`. Renamed to fit the pattern: `rest.request`/`rest.response` → `rest.before.request`/`rest.after.request`; `plugin.requirements` → `plugin.before.requirements` + new `plugin.after.requirements`; `register.*` → `register.before.*` + `register.after.*`; `render.head`/`render.content` → before/after pairs; `render.body.start`/`.end` → `render.before.body`/`render.after.body`; `schedule.run` → `schedule.before.run`/`schedule.after.run` around jobs declared in `schedules`. Limited user record by default; `users:full` opt-in (derived tag) requires `privacy.export`/`privacy.delete`. One API version.
0y. **MCP separation, runtime tests, trust flags.** haxcms-mcp stays stand-alone; core tools stay hand-written there, migrating to `x-hax-mcp` later. CLI install runs Node tests only; PHP compatibility is attested by the official release pipeline and source. Tested and signed are separate flags; hand-placed plugins load with guidance and a docs link; verify clears tested, not signed.
0x. **MCP plugin, test stubs, install-time tests, provenance.** MCP is an optional core plugin, system installed, enabled per site, blocked by HAXiam via new `blocked: true`; scoped revocable tokens; discovery operation for haxcms-mcp; core `mcp.*` config migrates into it. Generated test cases are commented-out passing stubs. The CLI runs plugin tests at install and update. Hand-placed plugins are flagged not tested / not signed and need confirmation to enable; `hax plugin verify` clears the flag.
0w. **MCP, prompts hook, upgrades, tests.** Optional core MCP plugin; operations opt in with `x-hax-mcp: true`. `register.prompts` collects prompts for the plugin screen and MCP. Generic upgrade skill plus optional per-plugin upgrade prompts. Tests required (`tests/cases/*.yaml` plus runtime tests) unless `untested: true`, shown as a derived tag.
0v. **AGENTS.md, prompts, skill audiences, tag limit.** AGENTS.md required like the README. Plugin screen shows README, skill links and copyable prompts (`docs/prompts.yaml`), with diagnose prompts next to the health chip. Skills: site, system (front-end discovery) and developer (read from the package, not duplicated). One category plus up to three author tags.
0u. **Discovery metadata and skills.** `category` (required, `other` allowed), `icon` (required), `docs.readme` (required), optional `screenshots`, author `tags` plus derived tags computed from the manifest that authors cannot set or hide. Plugin `skills` with `audience: site` (published into the site's `.well-known/agent-skills` while enabled) or `developer` (package only).
0t. **Disable cleanup, static, locales, scheduler.** Core clears caches and rebuilds managed outputs on disable; plugins tear down their own setup in disable hooks. `staticCapable: false` is a visible "needs a server" tag and a publish warning; the validator warns when routes exist without it. Two plugins overriding one locale key: priority wins, with a warning. Scheduler: CLI from cron preferred; an optional plugin can drive it from page requests and a timer; none on static sites.
0s. **Config hook scope, lock in git, move, site plugin list.** `config` filter on subscriptions (own by default, specific ids, or `*` incl. reads); read hooks added. Site lock config committed with the site's git; `hax plugin restore`. Unsigned installs get a notice. `hax plugin move`. `site.json` records the plugins a site was made with; missing ones warn in that site's log on import.
0r. **Install, uninstall, versions, overrides, config hooks.** Install asks for tier (site default inside a site, else system) and whether to enable; typical is system install plus site enable. Uninstall only after disable and purges data. Installed versions and ranges are kept in a CMI lock config per scope. A site copy overrides a system copy with a warning. Offline tarball installs are supported. Validation and the exec scan run at install and update only. `config.before.save` / `config.after.save` added; requirements re-evaluated after save.
0q. **Log, status, ordering, scope, requirements, CLI.** One unified server-style log written by the log plugin; warn/error sets a status chip. `ctx.pluginEnabled(id)` for optional companions shown on the install page. `conflicts` warns. Hook order by `priority` (default 0) then cascade. System-enabled plugins cannot be turned off per site. `plugin.requirements` keeps a plugin enabled but inactive until met. CLI covers install from npm/git/path, enable, disable, uninstall, config, status, list, update and log, system-wide or per site.
0p. **Enablement failure and dependencies.** A failure while enabling turns the plugin off with a recorded reason. Dependents must be disabled before the parent, with the UI showing both directions. Repeated hook failures keep running and logging. Log plugin and health badge: see item 12.
0o. **Extra fields and veto.** A plugin must declare the schema it extends; undeclared added fields are warned about and discarded. A veto fails the whole operation with an error to the caller. Failures (including detached hooks) must be surfaced as plugin health; see item 12.
0l. **Hook return contract**: return the updated subject (PHP parity); `ctx` is the context object with `veto`, `warn`, `settings`, `storage`, `log`, `fetch`, `respond`. Timeouts: 5 s before hooks, detached after hooks 60 s, no emergency switch. Overwrites by a later hook log a warning.
0m. **Render pipeline and injected singletons.** `output.alter*` replaced by `render.before/head/content/body.start/body.end/after`; singletons are written by `render.body.end` with settings baked in; SSR runs in `render.content`; caching via `render.before` short-circuit plus `render.after` store.
0n. **Process execution.** No general exec; `exec:run` capability plus an `exec` command list, statically scanned.
0f. **Hook subject, mutation and previous.** Subject by reference; before and after hooks may both change it; `ctx.previous` on update; page and manifest saves and git commits have their own hooks (added `page.*`, `manifest.*`, `git.*`). Return shapes are still open (item 6).
0g. **Formats formalized.** `config/datastores.yaml`, `config/entities.yaml` and `registries/locales/*.yaml` have schemas (`schema/`) checked by the validator. Locale overlays are flat per plugin, merged per key.
0h. **Themes.** `terrible` is deprecated and folds into `hidden`. Regions become their own plugin and storage type; themes still render them via `site-region`. A child theme falls back to the parent's registry entry. Disabling a plugin whose theme is in use is refused.
0i. **Appstore.** Merge uses the plugin loading cascade; secrets stay in plugin config (CMI) and are brokered by the plugin's routes; core providers will be peeled off into plugins.
0j2. **Themes and skeletons.** A skeleton whose theme's plugin is disabled falls back to the default theme with a warning; disabling a plugin whose theme is in use is refused (0h).
0j. **Assets and capabilities.** Asset ids are paths under `frontend/dist/` with `sha256-` hashes. `network:egress` and `settings:secret` are enforced first; the rest are declared, shown and audited.
0k. **Conformance runners and consumption.** `create` uses both backends from each repo, so the cases and harness must be stand-alone or published with the plugin examples package (`files` now includes `conformance/` and `examples/`). Runner adapters per backend are still to write.
0c. **Manifest `uuid` is required**, generated once by `hax plugin create`. The site UUID is the root `id` of `site.json`.
0d. **Moving a core setting into a plugin.** Saved as part of the plugin's configuration (CMI), removed from the global form, migrated from `site.json` by the plugin's install hook on first enable (spec/06, spec/07). Candidate future splits are in spec/07 section 7.3.
0e. **Hook subject.** The context carries the thing the hook is about (entity, page or manifest, plugin, site, user, request/response); per-hook fields are still open (item 6).
0. **Namespacing is by design.** A plugin is limited to one `tagPrefix`, deliberately (one namespace per plugin). The child theme in the example is `awesome-awesomer-theme` for that reason. (Was gap 3.)
0b. **Version scheme.** HAX versions are calendar style: year, month, then the release number within that month (`26.8.1`). Plugin and platform versions are compared as dotted numbers, which the semver syntax already accommodates, so `requires.haxcms` and dependency ranges use semver range syntax over calendar versions. (Was gap 4.)
1. **Public and rate-limit keys.** The spec said `public: true` per operation, but OpenAPI only allows `x-` extension keys. Now `x-hax-public: true` and `x-hax-rate-limit`.
2. **`hax validate`.** `hax audit schema` already exists in https://github.com/haxtheweb/create and shells out to each schema repo's validator. The spec now extends that command instead of adding a new one.

## Need a decision
20. **Extracting an always-on feature.** Today every editor gets the five keyless appstore apps (open-media-apps); as an optional pack they would disappear from existing sites unless something turns the pack on. Options: make such a pack `required` until a later release, or have the HAXcms release that extracts it run a one-time core upgrade step that enables it on every existing site (new sites then start without it). The same question applies to feeds, sitemap and search, which every site has today.
19. **Front-end work implied (webcomponents).** app-hax renders dashboard contributions and slots, registers operations from the unified contract, and listens for `hax-dashboard-open`; a small DDD chip element. Belongs to the later draft PRs.
17. **Skeleton `site.plugins`** needs a PR to https://github.com/haxtheweb/json-outline-schema.
15. **Backend adapters.** The reference harness runs executable cases in memory (Node and PHP). Adapters for the real haxcms-nodejs (in-process) and haxcms-php (CLI bridge) backends come with the draft backend PRs.
12. **Roles and permissions** for who sees health, the log, and who may install, enable and configure plugins at each scope.
13. **Merlin options from an endpoint.** Declarations stay and frontend registration is allowed. A backend-served option listing is future work.
